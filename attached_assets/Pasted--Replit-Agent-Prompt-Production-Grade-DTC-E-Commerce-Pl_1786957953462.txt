## PROMPT START

You are building a **production-grade single-brand DTC e-commerce platform** for a real Bangladeshi business (fashion attire + cosmetics). This is not a demo — treat it like a paid client project. Follow every rule below exactly. Do not skip steps or take shortcuts to "finish faster."

### Stack (do not substitute)

- **Frontend:** Next.js (App Router) + React + Tailwind CSS + HeroUI v3
- **Backend:** Express.js (separate service, not Next.js API routes)
- **Database:** MongoDB (Mongoose ODM)
- **Auth:** Better Auth (customer accounts + admin role)
- **Payment:** SSLCommerz (sandbox first) + Cash on Delivery (COD)
- **Image hosting:** placeholder URLs for now (design the schema so Cloudinary/S3 can be swapped in later without a migration)

### Business requirements

- Single brand, single currency (BDT, ৳)
- Product catalog spans two categories: **fashion attire** and **cosmetics**
- Products may or may not have variants:
  - If a product has variants, each variant has an optional `color` and/or optional `size`, plus its own SKU and stock count.
  - If a product has no variants, it uses a single stock count directly on the product.
- Expected volume: ~50 orders/day at launch — do not over-engineer with Redis/queues/microservices; a well-indexed MongoDB and a single Express service is enough at this scale. Design cleanly so these can be added later if volume grows.
- One founder runs the whole business — the admin role needs full control (no need for granular staff permissions yet), but structure the User role field so more roles can be added later without a schema change.
- Marketing: coupon codes (flat or percentage discount, usage limits, expiry) must be supported.
- All product photography/branding will be placeholder for now — do not block functionality on real assets.

### Pages required

**Customer-facing:**
`/`, `/collections`, `/collections/[category]`, `/products/[slug]`, `/cart`, `/checkout`, `/order-confirmation/[orderId]`, `/account`, `/account/orders`, `/about`, `/faq`, `/shipping-returns`

**Admin (separate protected route group, e.g. `/admin/*`):**
`/admin` (dashboard), `/admin/products`, `/admin/products/new`, `/admin/products/[id]/edit`, `/admin/orders`, `/admin/orders/[id]`, `/admin/coupons`, `/admin/coupons/new`

### Data model (design this first, before writing any UI)

Entities: `User`, `Product` (with optional embedded `variants[]`), `Order` (with embedded `items[]` that snapshot title/price/sku at order time — never trust client-submitted prices), `Coupon`.

- Every price shown to the customer at checkout must be recalculated server-side from the database. Never accept a price or total from the client as truth.
- Order stock must be decremented atomically (use MongoDB's `findOneAndUpdate` with a stock >= quantity condition) to prevent overselling when two customers buy the last item simultaneously.

### Payment integration rules

- Implement SSLCommerz in **sandbox mode** first. Get sandbox store credentials before writing checkout code.
- The order's `paymentStatus` must only change to `paid` when the **SSLCommerz IPN (webhook)** is received and independently validated via SSLCommerz's server-side validation API — never trust the browser redirect alone, since it can be closed or interrupted.
- The IPN handler must be **idempotent**: if SSLCommerz sends the same transaction ID twice, the order must not be fulfilled twice or have stock decremented twice.
- COD orders skip the payment gateway entirely but still go through the same order-creation and stock-decrement logic; `paymentStatus` stays `pending` until the admin manually marks it paid/delivered.

### Engineering rules (follow all of these without exception)

1. Validate every request body on the server (use `zod` or `express-validator`) — never trust client input, including from your own frontend.
2. Never expose secrets (SSLCommerz keys, DB connection string, Better Auth secret) to the browser — server-side env vars only.
3. All admin routes must check the user's role server-side on every request, not just hide UI elements client-side.
4. Handle loading, empty, and error states on every page that fetches data — no blank screens or unhandled promise rejections.
5. Use consistent API error response shape across all endpoints, e.g. `{ success: false, message: string, code?: string }`.
6. No placeholder `TODO` logic in checkout, payment, or stock-decrement code — these must work fully, even with placeholder product images.
7. Write the product/order/coupon Mongoose schemas with proper indexes (`slug`, `sku`, `couponCode` should be indexed/unique where relevant).
8. Optimize images with Next.js `<Image>` even for placeholder URLs, so swapping in real photos later requires no code change.
9. Mobile-first responsive layout — most BD e-commerce traffic is mobile.
10. Add basic SEO: meta tags per product/collection page, sitemap.xml, robots.txt.
11. Log errors server-side (console is fine for now, structure it so a real logger like pino can be swapped in later).
12. Rate-limit the checkout and coupon-apply endpoints to prevent abuse.

### Build order — implement in exactly these phases, and stop for my review after each one before continuing

1. **Project scaffolding** — Next.js frontend + Express backend as two separate services in this Repl, MongoDB connection, environment variable setup, empty deploy-ready skeleton.
2. **Data models** — Mongoose schemas for User, Product, Order, Coupon exactly as described above.
3. **Auth** — Better Auth wired up with customer + admin roles, protected admin routes.
4. **Product catalog** — storefront browsing (collections, product detail, variant selection) reading from seeded placeholder data.
5. **Cart** — add/remove/update quantity, persisted per session/user.
6. **Checkout (no payment yet)** — address form, order summary, creates an Order with `paymentStatus: pending`, server-side price recalculation and stock check.
7. **SSLCommerz integration** — sandbox session init, redirect, IPN handling with validation and idempotency, plus COD as the alternate payment method.
8. **Admin panel** — product CRUD, inventory editing, order management (status updates), coupon CRUD.
9. **Polish** — SEO tags, image optimization, error/loading/empty states everywhere, basic input validation audit across all endpoints.
10. **Pre-launch checklist** — review security (auth checks, input validation, webhook idempotency), confirm no secrets are client-exposed, test the full guest checkout flow end to end in sandbox.

Do not jump ahead to a later phase until I explicitly confirm the current phase is done and reviewed.

Start with **Phase 1 only**. Show me the folder structure and ask any clarifying questions before writing code.
